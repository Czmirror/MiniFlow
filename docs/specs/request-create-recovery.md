# 申請作成後の復帰仕様

- 目的: 作成成功後に提出・表示の処理が失敗しても、保存済み申請を新規作成し直さず復帰できる。
- 範囲: MiniFlowの新規作成画面からの保存・提出。API・DB・権限・永続的な重複防止は変更しない。
- 用語: 「作成済み」は、作成APIの成功応答と対象IDを受け取った状態を指す。通信失敗だけでは作成されなかったと断定しない。

## 受け入れ条件

- AC1: 作成成功が確認できたら対象IDを詳細画面へ保持し、作成フォームを初期化する。後続処理の失敗で新規作成状態へ戻さない。
- AC2: 提出が失敗・結果不明なら、保存成功と提出結果不明を区別して説明する。最新の詳細を取得し、既存の状態別操作を表示する。Draftなら同じIDで再提出でき、Pendingなら再提出を表示しない。自動的な提出再送はしない。
- AC3: 作成後の詳細取得が失敗しても対象IDを保持する。既存の再試行で同じIDの詳細を取得する。読み込み中・失敗・取得成功を区別し、過去の別申請を表示しない。
- AC4: 作成応答が得られなければフォーム入力を保持する。自動的な作成再送をしない。保存の有無が不明な可能性と、一覧で確認する案内を出す。ただし401・認証境界変更ではAC5の初期化を優先する。
- AC5: 送信中の連打と画面移動で作成要求を増やさない。認証・本人・所属・権限の境界変更後は、旧操作の成功・失敗・終了処理を新画面へ反映しない。401では既存のログイン復帰を使う。
- AC6: 日本語・英語で保存成功、結果不明、再試行を伝える。既存の詳細画面、キーボード操作、狭い画面の操作を維持する。

## 入力・エラーと対象外

title/bodyの入力条件とサーバー側の認可は現行仕様を維持する。作成後に提出が成功したのに応答だけ失われる場合があるため、「提出されていない」と断定しない。詳細取得で401を受けた場合は保存済み内容を表示し続けない。

作成応答自体が失われた場合の重複防止、別タブ・再読み込み後の同内容作成、古い画面からの上書き防止は今回の対象外。API・DBを変更して対応する案は別計画とする。

- 決定: 限定範囲で先行修正する。2026-11-04の会話で計画への「良いです」を受領した。公開API・DBの変更は含めない。
