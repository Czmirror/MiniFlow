# 申請削除画面の機能試験

仕様は`docs/specs/request-delete-ui.md`。2026-10-28、本番HTTPと架空メモリ保存先の専用Webで実施した。実DB・実ユーザーの申請は削除していない。対象は`e9c1d59`からの今回の実装差分。

| ID | 条件 | 手順と期待結果 |
| --- | --- | --- |
| DF1 | DU1 | 本人のDraft/Rejected、同teamのAdminでボタンが表示され、他人の一般ユーザー・Pending/Approvedでは表示されない |
| DF2 | DU2 | 確認に申請名と注意が出る。キャンセル/Escで未送信、詳細の編集入力を保持し、focusが元ボタンへ戻る |
| DF3 | DU3 | 確定時だけ削除し、元の一覧と状態条件を保つ。件数と集計を更新し、通常一覧から対象を消す |
| DF4 | DU4 | 連打でも送信は1回。503では詳細を保持し成功通知なし。409では自動再送せず再取得を案内、401ではログインへ戻る |
| DF5 | DU4 | 削除応答を遅延させ、認証/所属境界変更後の旧応答で画面が戻らない |
| DF6 | DU5 | 日英、広い/狭い画面、Tab・Enter・Escを確認。初期focusはキャンセル側で、確認画面内を移動できる |

## 実施結果

- DF1: 成功。一般利用者の本人Draft、管理者の本人Draft/Rejected、管理者の他人Draftで表示した。一般利用者の他人Draft、Pending、Approvedでは非表示。別チームとDeletedは単体試験で確認した。
- DF2: 成功。保存済み申請名と警告を表示し、未保存の件名を保持した。キャンセルとEscの後は元のボタンへfocusが戻り、削除送信数は0回だった。
- DF3: 成功。本人Draft削除後は自分の申請のDraft条件を保ち、26件から25件になった。別のDraft削除を含め、ダッシュボードは合計36件から34件、Draft26件から24件になった。管理者による他人Draftの削除後は通常一覧へ戻った。
- DF4: 成功。応答を10秒遅延させたダブルクリックでも送信は1回で、操作ボタンを無効化した。503では入力を残し、409では再取得案内を表示し、自動再送はなかった。削除APIの401でログインへ戻った。
- DF5: 一部成功・一部未実施。10秒遅延中に別の詳細を開いても旧成功が新詳細を閉じなかった。遅延中に一覧取得を401にしても、旧成功がログイン画面を戻さなかった。同じ画面の所属変更との同時操作は、送信中に更新ボタンが無効になるためブラウザでは未実施。所属・権限変更による世代更新と旧応答の拒否は独立レビューで確認した。
- DF6: 成功。日本語・英語、通常幅・390×844pxで確認した。キャンセルへの初期focus、Tabで確定ボタンへの移動、Escで閉じる操作、Enterで確定を確認した。狭い画面でも警告と両ボタンが収まった。native dialogの末尾からのTabはブラウザ側へfocusが移る挙動で、背面のアプリ操作には移らない。

実施者はCodex、手段はCUAの実ブラウザ操作。専用Webは`localhost:43106`、APIは`localhost:43107`。ブラウザのerror/warningログは0件。画像・fixture・カウンター・ログはローカルの`.harness/reports/delete-ui-*`に保存し、使い捨てデータはプロセス終了で破棄する。
