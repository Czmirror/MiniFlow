## 結果の根拠

- LF1/LF2: 全体46件の2ページ目（21〜40件）、本人Draft21件の2ページ目、承認待ち21件の2ページ目で、詳細から同じ一覧・ページへ戻った。別画面やダッシュボード経由でも保持した。全体一覧のApproved条件への変更は1ページ目になり、承認待ちの2ページ目は維持した。ダッシュボードはPending21〜17の先頭5件を表示した。
- LF3: 本人Draftの最終ページに1件だけ残る状態から削除し、Draft20件・1ページ目へ戻った。fixtureの取得記録は削除後に2ページ目、補正先1ページ目をそれぞれ1回だけ取得していた。詳細を再度往復しても1ページ目を使った。本人Rejectedの最後の1件を削除すると、条件に一致しない旨と0件・1ページ目を表示した。
- LF4: Draftの成功・503失敗を6秒遅延させ、Approved条件や承認待ちへ移動した。旧応答が到着しても新条件・承認待ち2ページ目を維持した。401でログインへ戻り、再ログイン後は承認待ちの1ページ目だった。架空本人のteamを1→2→1と変更しても旧2ページ目は復活せず、AdminからApproverへの変更でも1ページ目になった。Web再読込でも1ページ目からになった。ブラウザ結果と純粋状態試験のreset条件を照合した。
- LF5: 承認待ち2ページ目を503にすると、空の一覧ではなくエラーと再読み込み操作を表示した。障害解除後の再試行は21件目・2ページ目へ戻った。
- LF6: 日本語から英語へ設定を変えても承認待ち2ページ目を保持した。390×844pxでEnterによるPrevious/Nextを操作し、取得完了後の1ページ目と2ページ目を確認した。表とナビゲーションは既存の横スクロールを維持し、ページ送りは画面内に収まった。

ブラウザのerror/warningログは0件。証拠はGit対象外の`.harness/reports/list-position-return-wide.png`、`list-position-return-narrow.png`、`list-position-counts.json`。fixtureはDB接続を持たず、終了するとデータは破棄される。最初のサーバー起動はsandboxのbind制約で失敗し、専用loopbackポートの起動許可を得て再実行した。製品の不具合ではない。
