# 本人の所属・権限変更後の画面同期

ユーザー管理で自分を更新した直後に、所属・権限・表示言語を画面へ反映する。
所属や権限が変わると旧情報と未保存の文面を消し、別チームへの持ち越しを防ぐ。
人間による見た目の受け入れ、実機・他ブラウザ・200%拡大は未実施。

## 実装

`managedUserChange`で本人/他人、プロフィールだけ/所属境界の変更を判定する。状態そのものは`MiniFlowApp`が所有する。PATCH応答を使って本人情報とフォームを同期し、所属変更では既存の申請取得hookをresetする。旧クライアント集計や別の保存層は追加していない。

所属・role変更では選択詳細・履歴・承認理由・未保存申請・ユーザー作成入力・パスワード入力を破棄する。表示名・言語だけなら申請文面は維持する。Adminのままならユーザー一覧を新情報で取得し、降格時は取得しない。

保存失敗でeditorが先に閉じていた箇所も修正し、成功した場合だけ閉じる。認証破棄時にセッション世代を進め、古い更新の成功・失敗・finallyが新しい画面を変更しないようにする。セッション破棄自身がloadingを解除する。

仕様は`docs/specs/account-context.md`、試験は`docs/tests/functional/account-context.md`と`docs/tests/unit/account-context.md`。

## 検証と境界

Codexが2026-10-27に、DBへ接続しない本番HTTP＋既存のメモリ保存先fixtureで実施した。架空ユーザーと2チームだけを使い、サーバーの認可・更新routeは本番コードを呼んだ。秘密鍵は試験専用のダミーで、実環境の設定は読んでいない。

流れは「ユーザー管理の保存 → 既存API → メモリ保存先 → 更新応答 → 本人の判定 → 画面reset → 新しい所属の申請取得」。試験専用のHTTP hookだけで3秒遅延・503・401を与えた。製品コードに試験用分岐はない。

| 確認対象 | 結果・証拠 |
| --- | --- |
| AC1/FT1 | 旧teamの申請取得を3秒遅延させて本人をteam-2へ変更。通知とloadingの後、全件数2、作成フォームの件名/本文は空、team-2を確認 |
| AC2/FT2 | team変更後のAdmin管理一覧を再表示できた。Applicantへ変更すると管理ナビ0件、役割が申請者となり、入力文面も消えた |
| AC3/FT3 | 表示名更新とja/en言語変更では未保存の件名/本文を維持。他人のteamを変更しても本人のteam-2と文面を維持 |
| AC4/FT4 | 503では保存ボタンと編集中のteam値が残った。3秒遅い保存応答中に401を受けるとログインへ戻り、その応答到着後もLoginが表示された |
| 型・単体 | 型検査と18ファイル219テストが成功。判定関数の追加5ケースを含む |
| 実ブラウザ | 最終コードを再読み込み後のconsole error/warnは0件。画像はGit対象外の`.harness/reports/account-context.png` |

ブラウザ確認で、本人がAdminのままteamを変更したあとにusersを消したままにする問題を発見し、Adminの場合だけ再取得するよう修正した。初回の試験入口はrootのモジュール形式でtop-level awaitが使えず起動前に失敗したため、async入口へ直して再実行した。いずれも未解消として隠していない。

旧詳細・承認理由・パスワード入力の破棄はソース確認で、全入力を埋めたブラウザ再現は未実施。実DB検証は保存処理に変更がなく、今回の計画もメモリ試験のため適用外。実際の200%拡大等は前段階から未確認を引き継ぐ。
